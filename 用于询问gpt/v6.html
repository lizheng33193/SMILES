先给结论（按可修复优先级排好）：

  1. 把 eps 的对数变换去掉 是这次性能“雪崩”的主要原因。你的数据里 eps 的量纲非常大（n=118, 平均≈81,491，最大=223,900），和另外两列不在一个数量级上；你在 V2 里直接回归原始 eps，验证指标被它“拖爆”，调度器也被它牵着走，结果 R² 长期为负、Val RMSE 动辄几万。建议恢复 log10(eps) 的建模与评估（或用分位数/Robust 标准化），并把调度器的监控指标改成“不含 eps 的平均 RMSE”。
  2. token 处理链路不一致：你现在用的是 已经分好词的 processed_smiles，但 dataset.Randomizer 仍面向“原始 SMILES”做随机化；多数情况下它会返回 None 然后再走 utils.split() 二次切分，和当初做 vocab.pkl 的切分规则未必一致——这会极大抬高 <unk> 比例，导致编码特征“发白噪”。对“已分词列”请直接用 NoOpTransform（仅做 .split()），训练/验证都不要再用 Randomizer。参见 Randomizer 的实现和默认 collate_fn（以 0 作为 <pad>）可知当前做法确实是“针对原始 SMILES 的增强 + 0 号 pad”，与已分词列不匹配。
  3. 序列截断过重：你的 processed_smiles 令牌长度统计为 均值≈128，中位数=120，65% 超过 100；而 V2 的 SEQ_LEN=100，训练时大多数分子被截尾。建议把 SEQ_LEN 至少提到 180–220（你预训练时的最大帧长也是 220）。
  4. 其次是学习率/调度细节：V2 打印的 LR 是第一组参数（encoder）的 1e-5，看起来很小；head 的 LR=1e-3 其实没有打印出来。更关键的是你在调度器上用“平均 RMSE（被 eps 主导）”，会让两个更稳定的目标提前“被降 LR”。建议把 ReduceLROnPlateau 的监控值改成 mean(lam_abs, lam_em) 或者直接用 scaled 空间的验证损失。

我怎么定位到这些点的

  • 数据层面（你给的 data_train.csv）：

    • lam_abs(151) 与 lam_em(139) 的尺度 ~ 500–1,060，eps(118) 的尺度 12,500–223,900，重尾且方差极大；这解释了你截图里 “RMSE[abs, em, eps]=[108, ~148, **44,511**]”、平均 Val RMSE ≈ 14,922 的来源（基本被 eps 一列决定）。
    • processed_smiles 的 token 长度 中位数=120，65% > 100，使用 SEQ_LEN=100 时大范围被截断。

  • 代码差异：

    • 你在 V2 开头就注明了“本版不再对 eps 做 log 变换”，训练/评估的标尺和损失都在 原始尺度 上（这和你旧版 Notebook 里打印的 eps_log 指标明显不一致）。
    • Randomizer 明确是面向原始 SMILES做随机化；若 randomize 失败就走 utils.split(sm) 再切分。你当前却把它用在 已分词的 processed_smiles 上，切分规则不一致（容易产生大量 <unk>）。同时 collate_fn 用 src == 0 做 pad mask（0 正是 <pad>），这部分没错，但前面的 token 流程不一致会先把特征搞坏。
    • 你新加的 encoder 池化策略（mean/max + penultimate）本身没有逻辑问题；而旧版预训练的 encode() 也是 “mean/max/首帧/倒数第二层首帧”的 4H 结构——二者本质一致，不会单独导致全面失效。
